# 作り直し手順書（別のAIに一から構築してもらう用）

このファイルは、同じ仕組み（セーブ代行 + PayPay送金リンク決済 + 自動実行）を、別の人のために一から作るときの手順です。
ゼロから作るAIにそのまま渡せるように、「何を作るか」「どの順番で作るか」「何を検証するか」を書いています。

---

## 0. 先に確認すること（作る前に必ず）

- **規約と法律:** 対象ゲームの利用規約、PayPay の規約（非公式APIの利用可否）、特定商取引法（有償で不特定多数に提供する場合の表示義務など）を、サービス提供者本人が確認すること。ゲームのデータを書き換えるサービスは、BAN・アカウント停止のリスクがある。利用者への説明責任も提供者にある。
- **PayPay は非公式Web APIを使う。** 仕様変更で動かなくなる。公式の加盟店APIではない。
- **個人情報:** 利用者の引継ぎコード・暗証番号は、それ自体が「ゲームアカウントの鍵」。保存・ログ・外部送信のすべてで扱いに注意する。
- **受取アカウント:** PayPay の受取側は、提供者本人の電話番号・パスワード・SMS認証。他人のアカウントを扱わない。
- **このリポジトリに含めないもの:** 過去に流用した Discord ボットの zip（トークン入りの `.env` が含まれていた）は使わない。

## 1. 全体の仕組み（これを作る）

```
利用者（スマホのブラウザ）
  │  ① 引継ぎコード・暗証番号・メニューを選ぶ
  ▼
Webサーバー（Flask + gunicorn）
  │  ② 「注文」を作る（金額はサーバーが計算。画面の金額は信用しない）
  │  ③ PayPayの送金リンクを受け取り、金額・期限・受取人を検証して入金を確認
  │  ④ 入金済みになったら、ゲーム処理を別プロセスで実行（キュー・枠の上限あり）
  │  ⑤ 完了したらコードを表示（暗号化して3日保存）
  ▼
管理画面（/admin、管理者パスコード）
  - PayPay受取アカウントの登録（SMS認証）
  - 未完了の注文の確認・再確認・手動の支払い済み・停止
  - 取引履歴（利用者ID・送金者・金額・状態）
```

### 注文の状態（これが一番大事。ここがずれると二重払い・払い損になる）

| 状態 | 意味 | 次に起きること |
|---|---|---|
| `unpaid` | 注文作成済み・未払い | 利用者が送金リンクを貼る |
| `paying` | 送金リンクを確認中 | 結果で他の状態へ（二重押し防止の一時状態） |
| `hold` | PayPayで保留中 | サーバーが90秒ごとに再確認。入金されたら自動で実行 |
| `paid` | 入金確認済み・未実行 | 「実行を開始」で `starting` へ |
| `starting` | 実行を開始する処理中 | 開始できたら `started`。途中で再起動したら `paid` に戻す |
| `started` | 実行中 | 完了で `done`、失敗・中断は `paid` に戻して再実行可 |
| `done` | 完了 | コードを表示（3日保存） |
| `dead` | 自動では確定できない | 管理者が確認（再確認・支払い済み・停止） |

**鉄則:**
- 開始できるのは `paid` だけ。`paid` → `starting` への変更は、ロックの中で1回だけ行う（同時押しで二重実行しない）。
- 同じ送金リンクは、1回の実行にしか使えない（台帳で一意に管理。`used` フラグ）。
- 「確認できない」ときは `dead` にして人が見る。自動で `unpaid` に戻すと、リンクが記録済みで行き詰まる。
- 支払いの確認にはタイムアウトがある。タイムアウトや通信エラーの後に**自動で同じリンクを再送金させない**。

## 2. 作る順番（この順で作ると、途中で動作確認できる）

### 段階1: 画面と注文（PayPayなし）
1. Flask アプリを作る。`PAYMENTS_ENABLED=0` で決済を無効にできるようにする（開発用）。
2. 利用者の識別: サーバーのセッションに乱数（`job_owner`）を入れ、Cookieで保持（30日）。ログインは作らない。
3. 注文API:
   - `POST /run`: 入力を検証し、**金額をサーバーで計算**して注文を作る。レスポンスは `{order, amount, breakdown}`。
   - `GET /api/orders/mine`: 自分の未完了の注文の一覧。
   - `POST /api/orders/<id>/claim`: 注文番号で別の端末から再開（注文番号は推測できない長さの乱数）。
4. 料金は1か所（`PRICES` と `compute_amount()`）にまとめる。画面の表示も同じ値を使う。
5. テスト: 金額の計算、他人の注文が見えないこと、注文番号での再開、入力の検証。

### 段階2: PayPay受取（最も慎重に作る部分）
1. 暗号化: 認証情報・注文・台帳は、Fernet（対称鍵）で暗号化して保存。鍵は環境変数（`PAYPAY_ENCRYPTION_KEY`）で、ソースには置かない。
2. ログイン: 電話番号・パスワードでOAuth（`grant_type=password`）→ SMSのOTP（`grant_type=otp`）。結果のアクセストークンと `token` Cookie を暗号化して保存。期限切れ前に再ログイン。
3. リンクの形式: `https://pay.paypay.ne.jp/<英数字6〜128文字>` だけ許可。前後の余計な文字、複数のリンクは拒否。
4. 受け取りの手順（1回の受け取りで必ずこの順番）:
   1. `getP2PLinkInfo` で状態を取得（GET）。
   2. **検証:** 結果コード `S0000`、`orderStatus == PENDING`、金額が注文の金額と一致、`isSetPasscode == false`、`isLinkBlocked == false`、期限が未来、送金元と受取先が違う。
   3. 台帳（SQLite）に `INSERT`。同じリンクがあれば拒否（`UNIQUE`）。
   4. `acceptP2PSendMoneyLink` で受け取り（POST）。**このPOSTは自動で再送しない。**
   5. 応答が `COMPLETED`（または確認で `SUCCESS`）なら入金済み。
5. 保留: 応答に保留コード（`42007013`〜`42007016`）がある、または取得時に `isLinkBlocked == true`。→ 注文は `hold`。**止めない・再送金させない。**
6. 再確認（保留の解除後）: 同じリンクを `getP2PLinkInfo` で確認。
   - `SUCCESS` / `COMPLETED`: 入金済み。**受取人のIDが自分のアカウントか照合してから**支払い済みにする。
   - `PENDING` かつブロック解除: 金額などを再検証して、同じリンクで受け取り直す。
   - それ以外（取り消し・期限切れ）: `dead`（管理者確認）。
7. 状態名（`SUCCESS`・`COMPLETED`・`PENDING` など）は、実際の応答で確認すること。推測で決めない。**診断用に、最後に受けた状態コードだけを台帳に残す**（個人情報は入れない）。
8. セッション拒否（401/403）: 一度だけ再ログインして確認し直す（受け取りPOSTの前だけ）。
9. 失敗時の振り分け:
   - 待てば直る（通信・混雑・保留・ログイン切れ）→ `hold` のまま。
   - 直らない（期限切れ・取り消し）→ `dead`。
   - 結果不明（受け取りPOSTがタイムアウト）→ 台帳を `review` にして自動では再送しない。

### 段階3: 実行（ゲーム処理）
1. 実行は**子プロセス**で行う（ゲームのライブラリを壊れても本体を止めないため）。
2. 同時実行の上限（実行枠）と待機列。上限を超えたら「待機枠がいっぱい」と返し、注文は `paid` のまま（再送金不要）。
3. 同じ引継ぎコードの同時実行を禁止（HMACの値で管理。平文を保持しない）。
4. **重要:** 子プロセスが親のモジュールを読み込むときに、注文の照合や書き込みが走らないようにする（`multiprocessing` の spawn では、モジュールが子でも読み込まれる）。
5. 完了時: コードを結果として返す。注文には暗号化して保存（3日）。試運転の結果は保存しない。
6. 入力（引継ぎコード・暗証番号）は、開始したら注文から消す。

### 段階4: 利用者の画面
- 手順は4段階（アカウント → メニュー → 確認・支払い → 実行・受取）。
- 下のバーに「戻る／次へ」と金額を常に出す。
- 支払い画面: 金額・内訳・送金リンク欄・注文番号（コピー可）。「確認中」の表示は、押したあとすぐに出す。
- 保留中: 「保留中です。送金した側が解除すると自動で実行します」と出し、6〜45秒ごとに確認。
- 処理中: 他のタブを押せないようにロックし、離れるときに警告。
- 完了: コードと暗証番号を大きく表示、コピーボタン、ゲーム側の引き継ぎ手順、「控えました」にチェックするまで閉じられない。
- 利用者の画面は未完了の注文を6秒ごとに確認し、管理者が支払い済みにしたら自動で進み具合に切り替える。
- 入力内容（引継ぎコード・選択・手順）はタブ内に一時保存（再読み込みで消えない）。

### 段階5: 管理画面（`/admin`）
- 入口: 管理者パスコード（`ADMIN_PASSWORD`）。失敗が続いたら一時的に止める。
- PayPay受取アカウントのログイン・SMS認証。
- 未完了の注文: 状態、金額、利用者ID、最後の結果、PayPayの状態名。ボタンは「PayPayに再確認する」「実行を開始する」「支払い済みにする」「停止する」。入金記録のない支払い済み注文には警告。
- 取引履歴: 利用者ID・PayPay送金者・金額・状態・内容を一覧（利用者IDで絞り込み）。引継ぎコードは載せない。

### 段階6: 保留の自動確認と救済
- 保留の注文は、サーバーの常駐スレッドが90秒ごとに確認（1回最大5件）。利用者が画面を閉じていても入金されれば実行される。
- 起動時に、古いバージョンで行き詰まった注文を `dead` に移す処理を入れる（移行用）。

## 3. 設定（環境変数）

| 名前 | 必須 | 内容 |
|---|---|---|
| `SECRET_KEY` | ◯ | セッション署名。初回に生成して保存し、変えない |
| `PAYPAY_ENCRYPTION_KEY` | ◯（決済時） | Fernetの鍵。**紛失すると保存済みの認証情報・注文が読めなくなる** |
| `ADMIN_PASSWORD` | ◯ | 管理画面の入口。ファイル経由（`ADMIN_PASSWORD_FILE`）も可 |
| `PAYMENTS_ENABLED` | - | `0` で決済を無効（開発・検証用） |
| `PAYPAY_DATA_DIR` | ◯ | 暗号化ファイルの保存先（永続ボリューム） |
| `PAYPAY_LEDGER_PATH` | ◯ | 台帳（SQLite）の保存先 |
| `PORT` | - | 既定 8080 |

**ソースに秘密を書かない。** 本番では、秘密はPaaSの秘密情報機能か、サーバーの権限600のファイルに置く。

## 4. 本番への置き方

どれでもよいが、**永続ディスクが必須**（注文・台帳・PayPay認証情報を失うと、利用者の支払いが宙に浮く）。

- **Fly.io（トライアル後はカード登録が必要）:** `Dockerfile`（`exec gunicorn`で終了信号を届ける）、`fly.toml`（ボリューム、`kill_signal = "SIGTERM"`、`kill_timeout = "120s"`）。
- **VPS（国内・コンビニ払い可の会社）:** Docker Compose（アプリ + Caddy で自動HTTPS）。`docker compose up -d --build`。
- **Render などの無料枠:** 永続ディスクが消えるため不向き。

### デプロイで利用者を弾かない手順
1. 先にイメージをビルドする（サイトは動いたまま）。
2. 新しい決済確認・実行の開始を一時的に止める（`/api/drain` を管理者パスコードで呼ぶ。15分で自動解除）。画面側はエラーを受けても自動で再試行する。
3. 実行中・待機中・決済確認中の件数がゼロになるまで待つ（最大12分）。
4. 入れ替える。失敗したら `drain` を解除して終える。

## 5. テストの最低限（これが通らないなら公開しない）

- 金額: 各メニューの単価・まとめ方・試運転も同額。画面の金額とサーバーの金額が一致。
- 注文: 他人の注文が見えない・操作できない。注文番号で別端末から再開できる。
- 決済（PayPayはモック）:
  - 金額違い・期限切れ・取り消し・パスコード付き・ブロック中・受取人違い → 正しいコードで拒否。
  - 保留 → 解除後に同じリンクで受け取れる。
  - 受け取り済みのリンクを別の注文で使えない。同じ注文の貼り直しは確認になる。
  - 同時に2回「開始」しても1回しか実行されない。
  - 完了した注文をもう一度実行できない（無料で再実行されない）。
- 実行: 失敗・中断 → `paid` に戻る → 再実行できる。コード発行中の不明 → 自動で再実行されない。
- 再起動: 保留・支払い済み・実行中の注文が再起動後も残る。`starting` は `paid` に戻る。
- 画面: スマホ幅（390px）で、ライト/ダーク両方の表示。手順の切り替え、ロック、完了画面。
- 秘密: 引継ぎコード・暗証番号・PayPayの認証情報・リンクがログや履歴・画面のソースに出ていない。

## 6. 運用で決めておくこと

- **二重払いの扱い:** 同じ人が保留の末に払い直した場合、どちらを実行するか・返金するかを決める。管理画面で判断できるように、利用者IDと送金者IDを残す。
- **停止の基準:** 保留が何日続いたら `dead` にするか。
- **問い合わせ窓口:** 利用者は「ユーザーID」（使い方の画面に表示）と「注文番号」を伝える。
- **障害時:** 管理画面の「未完了の注文」を毎日確認する。`paid` のまま残っている注文は、利用者が困っている可能性が高い。
- **鍵の控え:** `PAYPAY_ENCRYPTION_KEY` と `SECRET_KEY` を、安全な場所（パスワード管理ツールなど）に控える。

```
- 作業を始める前に、docs/REBUILD_FOR_OTHERS.md の「0. 先に確認すること」を利用者に伝えて、了承を得る。
```

## 8. 既知の注意点（この仕組みの実績から）

- 保留の仕様は、実際の本番の記録で確認したもの（保留中は `PENDING` + `isLinkBlocked`、解除後は `SUCCESS`）。ただし PayPay 側の変更で変わり得る。診断ワークフローで状態を確認できるようにしておくこと。
- 過去に次の不具合が起きた。同じ過ちを避けること:
  - 保留を「使えないリンク」と誤判定して注文を止めた。
  - 入金済みのリンクの貼り直しを、台帳を見る前に「使用済み」で弾いた。
  - 管理者が「支払い済み」にしても、利用者の画面が気付かなかった（画面が状態を確認しにいっていなかった）。
  - 完了した注文が再実行できてしまった（無料で再実行）。
  - 子プロセスが親の注文を「中断」と誤記録した。
  - 再起動・デプロイで実行中の注文が消えた（`starting` の扱い、`SIGTERM` の待ち時間）。
- 「支払い済み」にした注文が、利用者の画面に出ないことがある。管理画面の「実行を開始する」で必ず確認すること。
