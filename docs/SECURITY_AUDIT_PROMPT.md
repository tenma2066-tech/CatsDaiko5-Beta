あなたは、この Flask アプリ（TN SHOP：にゃんこ／ツムツム／ぷにぷに代行の通販。PayPay の送金リンクで

## やること

1. 下の観点ごとに、実際のコードを読んで確かめる。推測で「たぶん大丈夫」と書かない。該当する
   `ファイル:行` を必ず挙げる。
2. 見つけたことを**深刻度（高・中・低）順**に並べ、各項目に次を書く：
   - どこ（`ファイル:行`）・何が問題か・どう悪用され得るか（具体的な入力や手順で）・直す方向（1〜2行）
3. 確証が持てないものは「要確認」として、確かめ方（どのテストを足す・どこを追えばよい）を書く。
4. 既存のテスト（`test_security.py` `test_hardening.py` `test_audit126.py` `test_v121.py`
   `test_admin_ops.py` ほか `test_*.py`）が、その観点をすでに守っているかも確認し、
   **テストが無い穴**を挙げる。
5. 最後に「すぐ直すべき上位5件」をまとめる。

## 前提（この店の決まり。ここは弱点ではない）

- 管理者ログインは時間では切らない（Cookie が続くかぎり有効）。2段階認証は任意。これは意図した仕様。
- 「みんなチート」が前提の、運営者本人のためのツール。ゲーム代行そのものの是非は点検の対象外。
- お客さんの認証は無く、ブラウザの乱数（`job_owner`）で本人を見分ける。注文番号は 128bit の秘密の値。
- 本番は Caddy（HTTPS・同一サーバー）の後ろ。`X-Forwarded-For` は Caddy が付け直す。

## 観点（この店に固有の急所）

### A. 秘密情報のあつかい
- `PAYPAY_ENCRYPTION_KEY` `SECRET_KEY` `ADMIN_PASSWORD(_FILE)` `ANTHROPIC_API_KEY`
  `TURNSTILE_SECRET_KEY` が、ログ・エラー応答・画面・バックアップ・ソース販売の zip
  （`source_pack.py` の INCLUDE/EXCLUDE/FORBIDDEN）に漏れないか。
- 注文に入るお客さんの機密（引き継ぎコード・暗証番号・LINE/メールのログイン・パスワード）が、
  管理画面・取引履歴・`/admin/api/*`・Q&A（`qa_bot.py`）・実績AI（`review_ai.py`）・
  管理操作の記録（`admin_ops.py` の admin_log）・CSV・例外ログに出ていないか。
  （設計では「LLM にはレビュー本文と星だけ」「履歴には秘密を入れない」。守れているか確かめる）
- `_order_to_json` / 保存（`paypay_gateway.save_orders`）で、秘密が平文のまま載っていないか
  （暗号化の前に何が入っているか）。

### B. 認証・セッション・管理画面
- `_is_admin` `_admin_login` `_admin_logout`（`app.py`）：ログイン状態の判定・Cookie の永続化。
  なりすまし・固定化（session fixation）・特権の昇格が無いか。
- CSRF：管理画面の POST は `admin_csrf` を `hmac.compare_digest` で確認している。すべての
  状態変更アクションが通っているか（`_admin_post` の分岐・`OPS_ACTIONS`・`/admin/api/*`）。
  GET の `/admin/api/*`（売上・注文検索・注文詳細・点検・ログ）は管理者チェックだけで CSRF は無いが、
  副作用が無いか（読み取り専用か）を確かめる。
- 総当たりよけ（`_too_many_fails`：IP ごと5回・全体30回／10分）と 2段階認証
  （`admin_2fa.py`）の、時間窓・全角数字・鍵の暗号化・使い回し防止。
- `SESSION_COOKIE_SECURE` / `HttpOnly` / `SameSite` の設定（`app.py` の Flask config）。

### C. 入力の検証と注入
- `/run`（注文）・`/api/reviews`・`/api/box`・`/api/qa`・`/api/*/order`・`/admin` の各入力。
  壊れた JSON・単独サロゲート・深い入れ子は `_scrub_json`/`_read_json` で処理済み。抜けが無いか。
- SQL：`admin_ops.search`（LIKE の ESCAPE）・`paypay_gateway` の各クエリにパラメータ化の漏れが無いか。
- パス・ファイル名：`_static`・`source_pack`・バックアップ・`PAYPAY_DATA_DIR` 配下の読み書きで、
  パストラバーサル（`../`）や想定外の書き込みが無いか。
- 金額・数量・ステージID・クーポンコードの範囲チェック（`pricing.py`・各 `validate_order`）。
  負の数・極端な値・オーバーフローで、0円や不正割引にならないか。

### D. お金の正しさ（この店で一番痛いところ）
- 注文の状態機械（unpaid→paying→hold→paid→starting→started→done/dead）と、
  「支払い済みの充当（credit）」「クーポンの reserve/consume/release」「送金リンクの
  付け替え（adopt_link）」で、**1回の支払いで複数回受け取る**／**他人の支払い・クーポンを奪う**／
  **0円で実行させる**経路が無いか。competition（同時リクエスト）も考える。
- `_human_ok`（Turnstile）が fail-open（Cloudflare に繋がらないと通す）である点の是非。
- レート制限（`_rate_ok`）が、決済・注文・実績・Q&A・クーポンに十分かかっているか。

### E. 外部との通信・LLM
- `review_ai.py` / `qa_bot.py`：プロンプトに注文の機密が混ざっていないか。お客さんの文章で
  システムプロンプトを乗っ取れないか（prompt injection。設計では「お客さんの文章は命令でなく質問」）。
  LLM の出力をそのまま画面に出していないか（`plain_text` の無害化）。
- `human.py`（Turnstile 検証）・`paypay_gateway`（PayPay API）・`github_runtime_store`（任意の
  GitHub 保存）で、TLS 検証無効化・SSRF・応答の過信が無いか。

### F. 情報の出方・DoS
- エラー応答・スタックトレース・`diag`・デバッグログが、内部構造や秘密を外に出していないか。
- 大きな入力・多数の同時注文・長時間周回で、メモリ/ディスク/実行枠（`_slots`）が枯渇しないか
  （`_gc_orders`・`MAX_*`・`ORDER_KEEP` の上限が効いているか）。
- `/admin` 以外の公開ページ・API に、認証なしで見えてはいけない情報が無いか。

### G. デプロイ・環境
- `deploy/vps/remote-setup.sh`・`docker-compose.yml`・`Dockerfile`：秘密の生成と保存、
  `.env` の権限、ポートの公開範囲、コンテナの権限。点検は**ファイルを読むだけ**（実行や接続はしない）。

## 出し方

- 見出しは深刻度（高・中・低）。各項目に `ファイル:行`・問題・悪用の筋道・直す方向・（あれば）
  足すべきテスト。
- 最後に「すぐ直すべき上位5件」。
- コードは変更しない。新しいファイルも作らない。報告だけ返す。
